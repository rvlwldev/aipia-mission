# 패키지 구조 및 아키텍쳐

레이어드 아키텍처를 기반으로 패키지 구조를 설계하고 각 레이어 내에서 도메인을 기준으로 패키지를 세분화했습니다.  
각 패키지는 명확한 책임을 가지며, 이를 통해 코드의 응집도를 높이고 결합도를 낮추어 유지보수성과 확장성을 고려했습니다.  
때문에 새로운 기능 추가나 기존 기능 수정 시 변경의 영향 범위를 최소화하고 수정 포인트를 쉽게 찾을 수 있습니다.

```
aipia/
├── _common/             # 공통 유틸리티, 예외 처리 등 범용적인 코드
├── _config/             # Spring 설정 (Security, JWT 등)
│   
├── api/                 # 외부 인터페이스 (REST 컨트롤러, 이벤트 구독자)
│   ├── rest/            # REST API 컨트롤러 및 요청/응답 DTO
│   └── subscriber/      # 이벤트 구독자
│   
├── application/         # 핵심 비즈니스 로직 (서비스, 도메인 모델, 포트)
│   └── domain/          # 비즈니스 및 도메인 관련 로직 
│       └──event         # 도메인의 이벤트 객체
│       └──exception     # 비즈니스 예외 (_common의 공통 예외 확장)
│       └──port          # 외부 시스템에 요구하는 기능
│   
└── infra/               # 인프라 계층 (어댑터, JPA 리포지토리, 외부 시스템 연동)
    └── domain/          # 비즈니스관련 관련 인프라 구현 (JPA 등의 외부 시스템 연동)
        └── *Adapter.kt  # application/domain/port 인터페이스의 구현체
```

* **`_common`**: 애플리케이션 전반에 걸쳐 사용되는 공통 유틸리티, 예외 처리 클래스 등을 포함합니다.
* **`_config`**: Spring Security, JWT 관련 설정 등 애플리케이션의 전역적인 설정을 담당합니다.
* **`api`**: 외부 시스템과의 접점을 정의합니다.
  - `rest` 하위 패키지에는 REST API 컨트롤러와 요청/응답 DTO가 위치합니다,
  - `subscriber`에는 이벤트 메시지를 수신하고 처리하는 로직이 포함됩니다.
* **`application`**: 비즈니스 로직이 구현되는 계층입니다.  
  각 도메인별로 서비스, 도메인 모델, 그리고 인프라 계층과의 통신을 위한 포트 인터페이스를 정의합니다.
* **`infra`**: `application` 계층에서 정의한 포트(인터페이스)의 실제 구현체(어댑터)를 포함합니다.  
  JPA 리포지토리, 외부 시스템 연동 로직 등 구체적인 기술 구현이 이 계층에 위치합니다.

## 확장성 및 유지보수성

가급적 클린코드의 이론을 따르기 위해 네이밍과 각 클래스의 책임, 변경 영향 범위 최소화 등을 고민했습니다.  
그래서 `application` 계층과 `infra` 계층 사이에 헥사고날 아키텍처를 채택했습니다.

현재 데이터베이스로 H2를 사용하고 있기에 포트 앤 어댑터 패턴을 적용하여 비즈니스 로직이 특정 DB에 종속되지 않도록 했습니다.  
NoSQL 데이터베이스나 외부 API 연동 시에도 `infra` 계층의 어댑터만 수정하면 되므로  
유연한 확장과 코드 수정에 대한 부담을 줄이기 위한 이유가 큽니다.

### 비즈니스 로직의 독립성

핵심 비즈니스 로직이 외부 기술(DB, 프레임워크 등)로부터 자유롭습니다.

### 기술 스택 교체의 용이성

비즈니스 로직이 특정 데이터베이스나 외부 시스템에 종속되지 않도록 했습니다.
변경되더라도 `infra` 계층의 어댑터만 교체하면 되므로, `application` 계층의 코드 변경 없이 비교적 유연하게 대응할 수 있습니다.

### 테스트 용이성

계층은 인터페이스에만 의존하므로, 단위 테스트 시 실제 인프라 구현 대신 Mock 객체를 사용하여 빠르고 안정적인 테스트가 가능합니다.

### 트레이드 오프 ...

인터페이스와 구현체가 분리되면서 코드의 양이 그만큼 늘어납니다.  
각각의 도메인과 비즈니스 로직의 책임이 명확하지만, 전체적인 큰 흐름을 파악하는 데 추가적인 노력이 필요할 수 있습니다.

## 회원가입 및 로그인

회원가입 및 로그인 기능은 `Spring Security`와 JWT로 구현했습니다.

추후 여러 서버 인스턴스, 모바일 앱, 또는 다른 서비스로 시스템이 확장될 경우,  
각 서비스가 사용자 세션을 공유할 필요 없이 독립적으로 인증을 처리할 수 있어 확장이 용이합니다.

또한 서버가 사용자 세션 정보를 저장할 필요가 없어 서버 자원을 절약하고, 수평 확장에 유리합니다.

## 주문 및 결제

주문 및 결제는 다음과 같은 기본적인 워크플로우로 진행됩니다.

1. **주문 생성**: 사용자가 상품을 선택하고 주문을 요청하면, `OrderService`는 회원 정보와 상품 정보를 확인하여 새로운 주문을 생성합니다.
2. **이벤트 발행**: 주문이 성공적으로 생성되면, `OrderCreatedEvent`가 발행됩니다.
3. **결제 처리**: `OrderEventSubscriber`는 `OrderCreatedEvent`를 구독하여 결제 처리를 시작합니다.  
   `PaymentService`는 주문 정보를 바탕으로 결제를 진행하고, 결제 상태를 업데이트합니다.

### 이벤트 처리로 사용자 응답 속도 향상

주문 생성과 같은 핵심 비즈니스 로직을 먼저 완료 후 빠르게 반환합니다.  
필수적이지만 시간이 소요될 수 있는 결제 처리와 같은 부가적인 작업을 비동기적으로 처리합니다.

### 도메인간 Decoupling

주문 서비스와 결제 서비스 간의 의존성을 줄여 각 서비스의 독립성을 높여 유연성을 높일 수 있습니다.

### 확장성 및 고도화 여지

현재 `PaymentService`는 주문 생성 이벤트에 대한 결제 처리만의 책임을 가지고 있지만,  
이벤트 기반으로 설계해서 여러 확장 가능성이 있습니다.

**병렬 처리**  
현재는 `PaymentService`에서 결제 처리가 순차적으로 진행되지만 쿠폰, 알림 등 여러 기능이 추가될 경우  
이벤트 구독자를 여러 개 추가하여 병렬적으로 처리할 수 있습니다.

**유지보수성**  
로직의 흐름이 이벤트로 인해 분리됨으로 특정 로직의 변경이 다른 로직에 영향을 주지 않아 유지보수가 용이합니다.  
즉, 결제 로직 변경 시 주문 생성에 대한 수정이 필요성이 없거나 현저히 적을 수 있습니다.
